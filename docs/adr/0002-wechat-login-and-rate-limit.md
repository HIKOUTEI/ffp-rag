# 问答接口用微信登录换 token + 限流防刷，后端不再完全无状态

小程序/App 直连公网后端，`/chat` 系列接口若匿名开放，陌生人抓包拿到接口地址即可
无限刷量，每个请求触发 3~5 次付费模型调用（改写 + 检索 embedding + 生成 + 热门榜 embedding），
账单可被一夜打穿。

## 决定

问答接口不再匿名开放。小程序 `wx.login` 拿 openid，后端签发短期 token；
`/chat` 系列必须携带 token。限流与每用户每日额度以 openid 为单位统计。

## 为什么不是「给接口加一个 API Key」

小程序/App 是公开客户端，任何塞进客户端的密钥都会随包分发到用户手机上，
等于公开，无法作为服务端密钥。因此直连场景下「静态 API Key」是假防护，
必须用真实用户身份（openid）+ 限流 + 成本上限的组合。

## 后果

- 后端引入登录态，`CONTEXT.md` 中「后端无状态」的表述需要修订：会话历史仍由前端携带，
  但用户身份/额度是服务端状态。
- 管理接口沿用既有 `ADMIN_TOKEN`（后端对后端，可藏密钥），与问答接口的鉴权是两套机制。
- **限流/额度存储：单 worker + SQLite 计数表（`usage(openid, day, count)`）。**
  这依赖「单进程」这一前提：内存限流计数与内存任务表（`_parse_tasks`、`health._tasks`）
  只在单 worker 下成立。**严禁改用多 worker（`--workers>1` / gunicorn），否则限流各存各的形同虚设，
  且解析/体检任务会出现「提交与轮询不在同一进程 → 轮询 404」。** 若将来要多 worker，
  须先把限流与任务表迁到 Redis。
