# 用户档案（信用卡/酒店/航司会籍）纯前端本地存储，后端不参与

小程序新增「我的」页，展示并管理用户持有的信用卡、酒店会籍、航司会籍。
这引入了「用户拥有的数据」，但本项目后端是无状态 RAG 知识库，没有用户数据体系
（ADR-0002 只引入用户**身份/额度**，不含用户业务数据）。若为此在后端加账号 +
数据表 + CRUD 接口，成本远超当前阶段所需。

## 决定

**用户档案（User Profile）完全在小程序前端维护，存微信 `Storage`，后端零改动。**

- 三类条目：航司会籍、酒店会籍、信用卡。字段只保留**相对稳定**的信息：
  归属品牌 + 等级/卡种 + 可选标识号（会员号/卡号）。
- **不存里程余额、积分余额**——这类数值更新过于频繁、易过时，维护负担大、展示价值低。
- 录入以**预置清单**为主：品牌、等级从内置列表选（选品牌后联动出该品牌的等级），
  可选标识号才手填，另给「其他」兜底手填。清单覆盖面**宽于 RAG 语料**
  （主流航司/酒店集团/发卡行），因为档案是「个人记录」而非「语料镜像」。

## 为什么不接入问答（这阶段）

档案与问答暂不耦合：问答仍只依据知识库回答，不自动注入用户档案。
但数据以**规整格式**（品牌/等级标准化）存储，为将来把档案摘要拼进 `messages`
做个性化问答预留接口，届时无需用户重录。

## 为什么不做航空联盟

联盟（星空/寰宇/天合）对权益有意义，但会增加录入/建模复杂度，且可由航司自动推导。
本阶段不建联盟类别、也不自动推导，保持模型最小。

## 后果

- 换设备 / 清缓存会丢失档案（本地存储固有代价）。可接受：这是个人便签性质，
  非权威账本。将来若上云，迁移到后端存储（需 ADR-0002 的登录态支撑）。
- tabBar 从两项（问答/关于）扩为三项（问答/我的/关于）。
- 需前端维护一张「品牌 → 等级清单」预置表，随主流产品变化偶尔更新。
