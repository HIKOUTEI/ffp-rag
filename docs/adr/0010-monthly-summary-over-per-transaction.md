# 奖赏钱以月结汇总为主，逐笔签账为可选

最自然的设计是逐笔记账：记下每笔消费，按规则算出该得多少 RC。
但那要求用户**每次消费后都来记一次**，而这类工具的历史表明没人会坚持。
一个没人用的账本算得再准也没有意义。

同时，汇丰的 Reward+ App 已经把结果算好了：余额、各类别的赚取汇总、即将到期，
一屏能看全。抄这 4~6 个数字只要一分钟，一个月一次。

## 决定

**月结记录**（一月一条，照 Reward+ 抄）是主数据。
**签账记录**（逐笔）是可选功能。

两者是**校准关系而非累加关系**：月结是权威值（来自汇丰），逐笔是预估值
（本地按规则算的）。逐笔用于月中推算，月结到账后覆盖校准。**相加会双计。**

## 月结里的流量与存量必须分开

月结一条记录同时装着两种性质完全不同的数：

| | 字段 | 能否跨月加总 |
|---|---|---|
| 流量 | 当月赚取（按类别） | **能** |
| 存量 | 余额、即将到期 | **不能**，是期末快照 |

13 个月的余额加起来是一个毫无意义、但看起来很像对的大数，用户会以为自己很有钱。
所以这两组在 schema 上就是 `flow` 和 `stock` 两个嵌套对象，不平铺——
平铺的话任何「近 N 个月汇总」的代码都会顺手把余额也加进去。

## 上限进度能只靠月结算出来

这是整个方案成立的关键：**月结 RC ÷ 费率 = 签账额**。
最红自主奖赏的 HK$100,000 历年额度用掉多少，由「最红自主奖赏」类别的累计 RC
除以 2% 反推即得，不需要任何逐笔数据。

代价是这只对**费率型**类别成立。定额型（优惠、Well+）除以任何费率都是垃圾数字，
所以规则与类别都带 `kind: rate | flat`，定额型一律不进反推。

## 门槛预测是月结覆盖不了的唯一缺口

内地餐饮 +3% 要求「每历月内地累计合资格签账 ≥ HK$1,200」才触发。
月结是**次月**才抄的——那时这个月已经结束，填进去只能事后核对，预测价值为零。

这是保留逐笔功能的全部理由，也是它唯一不可替代的用途。
所以逐笔的入口放在总览页门槛那一行（「记几笔签账才能算」），
不做首屏大按钮：它摆明是可选的。

## 后果

- 录入成本从「每次消费」降到「每月一次」。这是留存的前提。
- **外推必须剔除一次性收入。** 月结不区分 recurring 与 one-off——迎新那 800 RC
  和每月的 0.4% 混在同一份汇总里。只能靠规则集上的 `recurrence` 标记反向区分，
  并把剔除额显示出来，否则用户会怀疑预测偏低。
- **算不出来时一律返回 `null`，绝不返回 0。** 未登记、类别未确认、会籍年起算日
  没填，这三种情况下「已用额度」是未知而非零。0 会被画成「一点没用」的空进度条，
  那是个比「算不出来」危险得多的谎。每个计算值都带 `derivation` 字段说明来源。
- 本模块的三张表（`monthly_entry` / `spend_entry` / `user_setting`）必须纳入
  `GET /rail/export` 与 `DELETE /rail/account`。ADR-0007 的删除权与可携带权对它同样适用。
  不给各模块单开导出口，是因为那样客户端有机会只导一半而不自知。
