# 时刻表数据取自第三方 GTFS 镜像，每周同步并归档快照

「输入车次就自动补全全程停站」是铁路乘车记录的核心卖点，它需要一份覆盖全国
（含普速 K/T/Z）的列车时刻表。中国铁路没有官方开放 API。

可选路径有三条：直连 12306 的非公开接口、买第三方付费 API、用现成的开源数据集。

## 决定

**采用 GitHub 上的 `wensimehrp/chinese-railway-gtfs` 镜像，每周同步进本地 `rail.db`，
并归档每份原始数据作为运行图快照。**

## 为什么不爬 12306

要先用车次换内部 `train_no` 再查时刻表，全程要维护 Cookie/JSESSIONID、应对验证码
与反爬、自行限流。每次用户录入都要打一次外部请求，链路脆弱且对方随时可变。
更重要的是：这是**运行期的持续爬取**，风险敞口一直开着。

## 为什么不买第三方 API

授权干净，但按调用量付费、有限流、依赖对方可用性，且普速车覆盖常常不全——
而「覆盖全国所有火车」是本功能的既定目标。

## 为什么选它

- **离线可查**。同步一次，之后所有查询走本地 SQLite：零 per-request 成本、
  无限流、无外部依赖、不受对方接口变更影响。风险敞口只在每周一次的同步窗口。
- **覆盖完整**。实测 5386 站 / 13891 车次 / 123998 停站，13 类车次种别
  （高速动车、动车组、城际高速、市域、新空调快速、旅游、新空调直特/普快/普客/特快、
  市郊、普客、普快）全都在内。
- **体量极小**。原始包 1.6MB，落库后约 30~50MB。部署机只有 1.9G 内存且已在用 swap，
  这个量级毫无压力。
- **自带营业里程**。`stop_times.shape_dist_traveled` 是累计营业里程，
  实测 G1 北京南→上海虹桥 = 1318km，与京沪高铁官方里程一致。
  这让「里程」成为可精确展示的指标，而不是只能用坐标估算的近似值。
- **每周自动发布**，维护活跃。

## 接受的风险

**这份数据没有 LICENSE，且来源不透明。** 上游 README 原文：

> 时刻表与线路数据来自一铁路平台。考虑到相关影响，暂不公开获取数据的方法。

作者自己在规避来源。这意味着仓库随时可能消失或被下架。

缓解措施：

1. **自建 fork 作镜像**，不直接依赖上游可用性。
2. **归档每份快照**（约 83MB/年）。即使上游彻底消失，已有数据仍可用，
   且历史记录仍能还原到当时的运行图。
3. 内测阶段接受此风险。**公开上线前需重新评估**是否换成授权明确的数据源。

## 数据源的两处硬限制

这两条不是实现细节，它们直接决定了产品形态：

**没有开行日历。** `calendar.txt` 只有一行，13891 个车次全部标记为
`service_id=all`、天天开行至 2050 年，且无 `calendar_dates.txt`。
数据里不存在「某车次某天开不开」的信息。

因此**乘车日期不参与查询，只作为用户填写的记录元数据**。原本设想的
「输车次 + 日期 → 列出当日班次供点选」不成立。副作用是好的：跨日歧义
（始发日 vs 乘车日）自动消失。代价是周末线 / 隔日车填错了拦不住——记录工具可接受。

**没有线路几何。** 无 `shapes.txt`，只有车站坐标。地图轨迹只能是车站点连线，
在成昆线、青藏线这类大弯道区段会明显失真。真实线形需另引 OSM 并做 map matching，
不在第一版范围。

## 后果

- 同步必须走独立脚本（`python -m scripts.sync_gtfs`）+ 原子替换，
  由宿主 cron 周调。**绝不能在 FastAPI 请求进程里跑**——服务是单 worker（ADR-0002），
  会阻塞问答主链路。
- 坐标是 WGS84，而微信小程序 `<map>` 用 GCJ-02，必须转换，否则整体偏移 300~600m。
  转换在接口返回时做，库里保持 WGS84 原值以便将来对接其他地图与做距离计算。
- 时刻可跨日（实测最大 `77:30:00`，第 4 天），须以「自始发起的分钟数」存储，
  不能用 `datetime.time`。
- 29% 的车次号含 `/`（跨线换号），而车票只印其中一段，检索需按 `/` 分段匹配。
- 数据中有 783 个 `DUMMY_LINE_*` 伪车次（线路全线），同步时必须过滤。
- 无行政区划信息。「去过多少城市/省份」需另引边界数据做坐标反查。
