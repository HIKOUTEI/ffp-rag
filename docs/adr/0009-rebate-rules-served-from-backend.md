# 返现规则由后端下发，不随小程序发版

奖赏钱的加成规则几乎全是限时促销。内地／澳门扫码 +2% 与内地餐饮 +3% 都在
2026-12-31 到期；Travel Guru 的登记窗口历年在 9~10 月开合；最红自主奖赏的
自选类别每年底可改一次。规则变动的频率是「每季度」级别。

小程序发版要过微信审核，周期以天计，审核不通过还要改了重来。

## 决定

**规则集整份存后端，小程序不内置任何规则常量。**

`rewardcash.db` 的 `ruleset` 表，一份 JSON 存一行，append-only 版本。
`GET /rewardcash/rules` 下发，带 `ETag: W/"rc-<version>"`，支持 `If-None-Match` → 304。
小程序本地只做缓存。

## 为什么不把规则规范化成 SQL 表

规则只有 6 条、单人维护、永远整份读出整份下发，没有任何「按字段查规则」的场景。
规范化要拆三张表（规则 / 上限 / 条件）再配一套 CRUD 表单，而真正的约束
——费率型与定额型互斥、`reward_category` 必须在类别白名单里、规则与类别的 `kind`
必须一致——全都表达不成外键，仍得在 pydantic 里写一遍。

多一层 schema 换不到任何东西，两边还会漂移。

## 为什么整份替换而不是增量改单条

一份坏数据会让所有用户的 summary 同时算错，所以写入前必须**全量**校验。
既然每次都要全量校验，增量改单条就没有意义了——它只是把「校验整份」
伪装成「只改了一个字段」，风险一点没少。

整份替换 + append-only 版本还有个副作用是好的：出问题时能对照
「哪一版起算错了」，而不是只能看当前状态猜。

## 后果

- 促销换期只要在控制台改一份 JSON，所有端立即生效，不发版。
- 三个待确认字段（`qr-mobile-2` / `dining-3` / `travel-guru` 的 `reward_category`
  仍是 `null`、Travel Guru 三档未拆）可以随时回填。
- 代价：**校验不过一律不落库**，`GET /rewardcash/rules` 继续返回旧版本。
  控制台必须把 pydantic 的完整报错原样显示给维护者——字段路径是定位问题的唯一线索，
  包装成「保存失败」等于把它扔了。
- 代价：小程序首次打开总览页必须联网。本地缓存只能兜住第二次之后。
- `period_start` / `period_end` 的语义是**促销窗口，过期即从上限进度里消失**。
  常设的年度项目（最红自主奖赏）这两个字段留空，否则它会在跨年那天整条不见，
  用户最主要的赚取规则毫无提示地消失。「条款核对到哪天」由 `source.checked_at` 表达。
