# 纠错记录由前端上传快照，并为此把 doc_id 暴露给客户端

小程序用户给一条 AI 回答报错时，后端需要知道当时的问题、回答全文，以及**这次回答命中了库里哪几条知识**——
最后一项是管理员能快速修正的关键。有两条路拿到它：后端在每次回答后缓存一份（问题/回答/doc_ids）
并发一个 `answer_id`，前端报错时只传 id；或者前端把手上已有的东西原样传上来。

## 决定

**前端原样上传快照**（问题、改写后问题、回答全文、`sources` 含 `doc_id`、用户说明），后端只负责存。
为此 `store.search()` 开始带出 `doc_id`，`Source` 模型新增 `doc_id` 字段，并随非流式响应与
SSE `sources` 事件一起下发到客户端。

## 为什么不发 answer_id

`answer_id` 方案更"干净"——上行数据小、不可伪造、不用暴露内部 id。但它要求后端缓存每次回答，
也就是引入**服务端会话状态**。而本项目问答链路自始至终是无状态的（CONTEXT.md「会话」：
会话历史由前端每次请求携带），一旦开这个口子就要处理缓存过期、清理、进程重启丢失、
以及"用户报的是三天前那条回答"这类必然失败的场景。为一个低频的反馈功能引入这些，代价不成比例。

## 后果

- **内部 `doc_id` 暴露给公网客户端。** 可接受：id 形如 `frag-<uuid>`，无语义、不可枚举，
  且知识内容本来就通过来源展示给用户了。
- **上报内容可伪造。** 用户理论上能构造一条「问题/回答/doc_ids」全是编的纠错记录。可接受：
  上报需登录、有独立日限额，且纠错记录**只是给管理员看的待办项**——不自动修改知识库，
  每一次真实的库变更仍然经过人工确认并落进 changelog。伪造的代价只是浪费管理员一次扫视。
- **老消息报错拿不到 `doc_ids`。** 小程序此前不保存每条回答的 sources，历史消息报上来
  `doc_ids` 为空。与「库里压根没这条知识」是同一种表现，后台一并显示为「无关联知识」。
