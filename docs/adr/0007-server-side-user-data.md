# 乘车记录存服务端，并引入内部 user_id

铁路乘车记录是本项目第一份**长期累积、跨设备、属于用户本人**的数据。这与
ADR-0003 的既定路线冲突——那份 ADR 决定「用户档案完全在小程序前端维护，存微信
`Storage`，后端零改动」，理由是后端没有用户数据体系，为此建账号 + 数据表 + CRUD
的成本远超当时所需。

> **推翻 ADR-0003 的前提，但只推翻一半。** 见下方「为什么不顺带迁移用户档案」。

## 决定

**乘车记录存服务端，挂在内部 `user_id` 之下，而不是直接挂 openid。**

新增两张表（`auth.db`）：

- `user(id, created_at)` —— 内部账号
- `identity(provider, external_id, user_id, created_at)` —— 登录方式到账号的映射，
  现在只有 `provider='wx'`，`external_id` 即 openid

用户业务数据（`journey` 表）外键指向 `user_id`。

## 为什么必须存服务端

用户档案（会籍、信用卡）是**个人便签性质**，丢了重录一遍，十来条，几分钟的事。
乘车记录不是：它是逐年累积的、不可重建的个人史。记了三年的行程因为换手机就没了，
这个产品就废了。本地存储的固有代价在档案上可接受，在这里不可接受。

## 为什么不直接用 openid 当外键

`CONTEXT.md` 首行写明本项目服务「网页 React、微信小程序、**未来 iOS**」。
iOS 原生端拿不到 openid。若行程表直接存 openid，做 iOS 时要改表结构 + 迁移全部
历史行程 + 处理「同一个人两套数据」的合并。

现在加这一层的成本是**一张两列表加一个查询函数**；事后补的成本是数据迁移。
这不是过度设计，是成本差了一个数量级。

## 为什么不顺带迁移用户档案

**ADR-0003 对用户档案继续有效，会籍与信用卡仍存前端 `Storage`。**

两类数据的性质不同：

| | 用户档案 | 乘车记录 |
|---|---|---|
| 数据量 | 十来条，稳定 | 逐年累积，无上限 |
| 丢失代价 | 重录几分钟 | 不可重建 |
| 敏感度 | 含卡种/会员号 | 含个人行程轨迹 |

档案上云能带来的只有「换设备不用重录」，而代价是把信用卡卡号一类信息搬到服务端，
承担对应的安全与合规责任。收益不抵代价，**不做**。

破例仅限乘车记录。将来若档案也要上云，另开 ADR。

## 后果

- 本项目从此**存储用户个人信息**。行程轨迹属个人信息，上线前必须在小程序后台配置
  《用户隐私保护指引》并声明收集类型，否则审核不过。
- 必须提供删除能力：删单条、清空全部、注销账号。个保法要求，不是可选项。
- 越权防护成为常规要求：所有读写都要带 `user_id` 条件。查别人的记录返回 404
  而非 403——不泄露该 id 是否存在。
- 现有 `session` 表的既有问题（token 永不过期、无 openid 索引、每次 relogin 插新行）
  本 ADR 不修。openid 本身稳定，换设备后仍能正确找回数据，暂不构成阻塞。
