# Spec: 纠错记录（用户报错 → 管理员修正知识库）

## 背景

知识库的内容会过时（航司规则改了）、会录错（AI 解析抽歪了）、会缺失（压根没这篇文章）。
现状只有管理员单向的发现渠道：`/admin/health-check` 体检（时效性/盲区/矛盾）。
真正天天在用、最先撞见错误信息的是小程序用户，但他们的发现**没有任何通道回流**——
看到一个离谱答案，只能关掉。

## 目标

建立「用户报错 → 后台队列 → 管理员改知识库」的闭环。用户侧摩擦尽量低，
管理员侧尽量一屏内完成修正。

## 设计决策（经 grilling 敲定）

1. **归属**：管理员纠错队列，不是用户私人错题本。用户报错的**目的**是驱动知识库修正，
   不是个人收藏。
2. **上报入口**：每条 AI 回答下方（来源旁）常驻「👎 报错」，点开弹输入框
   「哪里不对？（选填）」，**说明不强制**。取上报量，接受一部分空白条目。
3. **记录内容**：问答快照 + **关联的知识条目 id**。管理员点开一条报错就知道该去改哪几条知识，
   而不是自己去 `/admin/docs` 里大海捞针。
4. **生命周期**：两态 `pending → done`，处理时填一句处理备注。不做四态工单流（单人维护）。
5. **聚合**：每次报错一条独立记录，不合并、不计数。前期量小，重复条目一眼能认出来。
6. **身份与限额**：走 `auth.require_user()` 验身份但**不扣提问额度**——不该惩罚愿意反馈的用户；
   另设独立的每日报错上限防刷。记录里存 `openid`。
7. **上报契约**：前端把手上已有的快照原样 POST 上来，后端只负责存。保持
   「问答无服务端会话状态」（见 CONTEXT.md「会话」）。代价：需暴露 `doc_id` 给客户端、
   上报内容理论上可伪造。详见 `docs/adr/0005-correction-report.md`。
8. **后台交互**：纠错卡片内联展示关联知识正文，就地编辑/删除（复用现有
   `PATCH/DELETE /admin/docs/{id}`），改完**手动**点「已处理」。不做「改了知识就自动标已处理」
   的联动——改的不一定是为了这条报错。

## 数据模型

`changelog.db` 新表 `corrections`（沿用现有 SQLite + 异常静默的写法）：

| 字段 | 说明 |
|---|---|
| `id` | 自增主键 |
| `question` | 用户原问题 |
| `rewritten` | 改写后的检索问题（可空） |
| `answer` | 回答全文快照 |
| `doc_ids` | JSON 数组，本次命中的知识条目 id。**可为空**——空表示库里没有对应知识，多半要补录 |
| `sources` | JSON 数组，来源标签快照（source/url/score/domain） |
| `note` | 用户说明，选填 |
| `openid` | 报错人 |
| `status` | `pending` / `done` |
| `resolution` | 处理备注，管理员填 |
| `created_at` / `resolved_at` | 时间戳 |

## 接口

- `POST /feedback/correction` — 用户上报。`require_user()` 验身份（不扣提问额度）+ 独立日限额。
- `GET /admin/corrections?status=pending&limit=100` — 列队列，默认只看待处理。
- `PATCH /admin/corrections/{id}` — 标记已处理 + 处理备注。

配套改动：`store.search()` 带出 `doc_id`（正文命中取 chroma id，别名命中取 `meta.parent_id`），
`Source` 模型加 `doc_id` 字段，非流式响应与 SSE `sources` 事件同步暴露。

## 术语（已写入 CONTEXT.md）

- **纠错记录 / Correction**

## 明确不做

- 不做用户侧「我的反馈」列表、不做订阅消息通知。用户报完只得到一个 toast。
- 不做错误类型分类（信息过时/内容错误/答非所问）。前期数据量小，分类统计价值有限。
- 不做后端 answer 缓存与 `answer_id`——见 ADR-0005。
- 不做赞/好评。当前只收负向信号。

## 验收

- 小程序：AI 回答下方出现「👎 报错」；点击弹输入框；选填说明后提交成功，toast「已收到，
  感谢反馈」，按钮置灰为「已反馈」；因聊天历史本就持久化到 Storage，重进小程序该标记仍在。
- 超过日限额后再报错，返回 429 且前端给出可读提示。
- 未登录（无 token）上报返回 401。
- 后台：纠错队列默认列出 pending；展开可见问答快照、用户说明、关联知识正文；
  就地改完知识后点「已处理」填备注，该条从待处理列表消失。
- 命中不到知识（库里没有）的报错，`doc_ids` 为空，后台显示「无关联知识（可能是库里缺）」。
- 纠错相关的任何异常都不影响问答主链路。
