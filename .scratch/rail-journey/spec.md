# Spec: 铁路乘车记录（自动填写 + 打卡地图）

## 背景

本项目至今是**无状态知识问答**：后端不存任何用户业务数据（ADR-0003 明确把用户档案
留在前端 `Storage`）。铁路乘车记录是第一个需要**长期累积、跨设备、属于用户本人**的
数据集——用户记了三年的行程不能因为换手机就没了。

同时它引入一类全新数据：**全国铁路运行图**。这是只读的公共参考数据，不属于任何用户，
也不属于 RAG 知识库（不参与检索、不参与问答）。

## 目标

用户在小程序里用最少的输入记下"我坐过哪趟车"，系统自动补全全程停站、时刻与里程，
并在地图上累积成一张属于他自己的铁路版图。

面向用户、内测阶段、覆盖全国铁路（含普速 K/T/Z，不只高铁）。

## 设计决策（经 grilling 敲定）

1. **时刻表数据源**：GitHub 上的 `wensimehrp/chinese-railway-gtfs` 镜像，每周同步。
   无 LICENSE、来源不透明，内测阶段接受此风险，自建 fork 兜底。详见 `docs/adr/0008`。
2. **后端归属**：现有 FastAPI 服务内的**独立模块**，不新建服务。路由前缀 `/rail`，
   独立 `rail.db`。决定性理由是复用现有微信登录态——拆服务就要做跨服务鉴权。
3. **身份**：引入内部 `user_id`，`identity(provider, external_id) → user_id`。
   现在只有 `provider='wx'`，为 `CONTEXT.md` 已写明的「未来 iOS」留口。详见 `docs/adr/0007`。
4. **历史补录**：允许手填，**不编造时刻**。同时从现在起每周归档 GTFS 快照，
   未来的记录能精确还原到当时的运行图。
5. **地图**：车站点连线，不做真实铁路线形（GTFS 无 `shapes.txt`）。
   轨迹几何存成独立字段，为将来引入 OSM 线形预留升级位。
6. **录入流程**：输车次 → 展开全程停站 → 点上/下车站 → 另填乘车日期。
7. **统计**：里程 + 站数 + 城市数 + 省份数。里程取自 GTFS 的累计营业里程，与票面一致。
8. **小程序位置**：第 4 个 tab「行程」。tabBar 变为 问答 / 行程 / 我的 / 关于。
9. **节奏**：先打通后端地基（可 curl 验证），再做界面。

## 数据实测结论（2026-09-13 版 GTFS）

下载 `output_gtfs.zip`（1.6MB）实测，**两项结果推翻了 grilling 阶段的初始设计**：

### ❌ 没有开行日历 → 日期降级为元数据

```
calendar.txt:  service_id,monday,...,sunday,start_date,end_date
               all,1,1,1,1,1,1,1,20260721,20500721
```

只有一行，13891 个车次全部共用 `service_id=all` 标记为天天开行至 2050 年，
且**没有 `calendar_dates.txt`**。GTFS 里不存在任何"某车次某天开不开"的信息。

因此：

- 原设计「输车次 + 日期 → 列出当日班次供点选」**不成立**——每天列出来的完全一样。
- **日期不参与查询**，纯粹是用户填写的记录元数据。
- 副作用是好的：跨日歧义（K1 始发日 vs 乘车日）**自动消失**，因为不再用日期匹配车次。
- 代价：周末线 / 隔日开的普速车，用户填了不存在的日期系统拦不住。记录工具可接受。
- 连带：**「班次 / Service」术语作废**，改用与日期无关的「车次时刻表 / Timetable」。

### ✅ 有真实营业里程 → 里程可精确计算

`stop_times.shape_dist_traveled` 是**累计营业里程（公里）**：

```
G1,06:30:00,06:30:00,STN_北京南,1,0
G1,10:13:00,10:15:00,STN_南京南,5,1023
G1,11:24:00,11:24:00,STN_上海虹桥,7,1318    ← 京沪高铁官方营业里程即 1318km
```

原设计因"里程算不准"而回避里程、改主打站数，该前提不成立。
用户乘坐区段的里程 = `dist[下车站] - dist[上车站]`，精确且与车票票面一致。
**里程与站数/城市数一并展示。**

### 其余实测事实

| 项 | 结果 | 影响 |
|---|---|---|
| `shapes.txt` | 不存在 | 车站连线是唯一选择，确认原决策 |
| 电报码 | 不存在。`stop_id` = `STN_<中文站名>` | 车站模型去掉电报码字段 |
| 跨线换号 | **3969 / 13891（29%）** 车次号含 `/`，如 `K551/K554` | ⚠️ 车票只印其中一段的号，检索**必须按 `/` 分段匹配** |
| 跨日时刻 | 11942 条停站 ≥ `24:00`，最大 **`77:30:00`**（第 4 天） | 时刻需按 `HH>24` 解析并折算天偏移 |
| 车次号唯一性 | 13891 条 `trip_short_name` 无重复 | 可直接用车次号做业务主键 |
| 站名歧义 | 北京有 9 个站（北京/东/西/南/北/丰台/朝阳/大兴/通州） | 因从停站列表点选，自动消解 |
| 规模 | 5386 站 / **13891** 车次 / **123998** 停站 | SQLite 轻松承载，约 30~50MB |
| 伪车次 | 783 个 `DUMMY_LINE_*`（线路全线），另带 7249 条停站 | 同步时必须过滤；文件内停站总数 131247 含这部分 |
| `route_id` | 真实车次为 `CLASS_*`，`route_long_name` 是车次种别，**共 13 类** | 可用于"坐过多少种车型"统计 |

车次种别全量（按车次数排序）：高速动车 5026、动车组 2924、城际高速 2860、市域 1079、
新空调快速 1024、旅游 310、新空调直特 189、新空调普快 161、新空调普客 145、
新空调特快 132、市郊 21、普客 12、普快 8。

## 术语

见 `CONTEXT.md`。核心是把**共享参考数据**与**用户数据**分开：

- **车次 / Train Number**、**车次时刻表 / Timetable**、**停站 / Stop**、**车站 / Station**
  —— 共享参考数据，只读，全体用户共用一份。
- **乘车记录 / Journey** —— 属于用户，= 车次 + 乘车日期 + 上车站 + 下车站。
- **运行图快照 / Timetable Snapshot** —— 每周归档的 GTFS 原始包。

⚠️ 刻意避开 GTFS `trip` 的直译"行程"，防止与用户的记录撞名。
⚠️ 铁路**不进** RAG 的 `domain` 取值（`airline`/`credit_card`/`hotel`/…）——
那是知识库分类，与行程记录无关。

## 明确不做

- 不做真实铁路线形（无 `shapes.txt`，需另引 OSM + map matching）。
- 不做晚点 / 实际时刻——GTFS 是计划运行图，不含实时信息。
- 不做车票 OCR、行程单导入。第一版只手动输车次号。
- 不把行程数据接入 RAG 问答。
- 不迁移现有用户档案（会籍/信用卡）到后端——维持 ADR-0003，理由见 ADR-0007。
- 不做多人协作、不做分享到好友/朋友圈（第一版先跑通记录本身）。

## 未决问题

1. **`CONTEXT.md` 领域范畴**：现定义为"航司里程/信用卡转点/酒店积分"，铁路不在内。
   本 spec 暂按「同一小程序下的第二条产品线」处理，不扩大 FFP 定义。待确认。
2. **服务器磁盘余量**：快照归档约 83MB/年，1.9G 内存那台机器剩余空间未知。
   不够则改为归档到自建 GitHub fork 的 Release。
3. ~~**记录字段范围**~~ **已定**：第一版只存最小集（车次 + 日期 + 上下车站 + 备注），
   席别 / 车厢座位 / 票价 / 照片不做，已按此实现。
4. **行政区划边界数据源**：现用阿里 DataV GeoAtlas 离线生成映射表。
   仓库只提交派生的 `station_id → 城市/省份` 映射，不提交边界几何。
   若将来要公开分发，需确认这份派生数据的许可边界。

## 上线前必办（非选择题）

- **隐私合规**：行程数据属个人信息，这是本项目首次收集用户数据到服务端。
  微信要求配置《用户隐私保护指引》并声明收集类型，现有小程序未配置，**不配会审核不过**。
- **删除与导出**：用户须能删除单条记录、清空全部、注销账号。个保法要求。
  → **已全部实现**（issue 06 + 11）：`DELETE /rail/journeys/{id}`、`DELETE /rail/journeys`、
  `GET /rail/export`、`DELETE /rail/account`。注销为真删：乘车记录、`identity`、`user`
  与该 openid 的全部 session 一并删除，旧 token 立即失效；再次登录会拿到全新 `user_id`。
  **剩下的是前端入口**——接口有了不等于用户找得到，issue 08 的「数据与隐私」区需接上这两个。
- **上游 fork 与 cron**：按 ADR-0008 自建 GTFS 镜像 fork（改 `GTFS_REPO` 环境变量即可），
  并在宿主配周调 cron 跑 `python -m scripts.sync_gtfs`。
