# 01 · 修复 _split_text 列表截断与序号粘连

Status: resolved

## 问题

见 `../spec.md`。核心两点：
1. `_split_text` 按字数硬切，把语义完整的列表/小节拦腰切断，导致 LLM 提取时丢档（如 `2.75N` 整档丢失）。
2. `1.` + `50N` → `1.50N` 序号粘连，anti-`1.50N` 指令未生效。

## 候选方向（待 grill / 定方案后再实现）

- **切分边界优先小节标题**：在 `_split_text` 里优先按小节/编号标题（如 `一、`/`二、`、`1.`/`2.`
  行首、`【…】`、`\n数字.\n`）切，而非纯字数，避免把一组里程碑档位切散。
- **块重叠（overlap）**：相邻块保留一定重叠字数，降低边界丢内容概率。
- **序号规整预处理**：抓取后、切分前，把 `\n1.\n` / 行首 `N.` 这类孤立序号与其后内容做规整
  （或还原成 `第N项：`），从源头消除 `1.50N` 粘连，不再只靠 prompt 兜底。
- **提高单块 max_len 或整篇不切**：12000 字上限下，评估能否让 LLM 一次吃完整篇，
  规避分块（需权衡 token 成本 / 输出截断风险）。

## 验收

- 用真实案例 URL（万豪攻略）重跑摄入，里程碑 **50N 与 75N 两档都完整提取**，
  序号不粘成小数。
- 另找 1–2 篇含长列表的公众号文验证不回归。

## Comments

### 2026-09-19 · 已实现，待真实入库验收

方案：**边界感知切分 + 块放大到 2500 + 序号规整**。没采用块重叠（相邻块重叠会放大
`parse()` 里按 `text[:80]` 去重的脆弱性，措辞稍有差异就会双份入库），也没采用整篇不切
（12000 字单次调用会让模型倾向概括少抽，且 JSON 输出有被 `max_tokens` 截断的风险，
与 `PARSE_SYSTEM` 的逐字保真直接冲突）。

改动：

- 新增 `backend/app/chunking.py`，把切分逻辑从 `ingest_url` 拆成**纯标准库**模块。
  拆开是为了回归脚本能在没有 openai/chromadb、也没有 API key 的环境里跑——
  `app.ingest_url` 一 import 就会经 `app.rag:6` 构造 OpenAI client，没 key 直接抛。
- 连续列表项（含各项折行、紧邻在前的引导行）归并为**原子单元**，装箱时整组不可分；
  `max_len` 1000 → 2500，从硬上限变软上限；超大列表组只在项边界下刀。
- `normalize_numbering` 把孤立序号行与下一行合并为 `第N项：内容`，措辞与
  `PARSE_SYSTEM` 第 75 行的示例对齐。
- 新增 `backend/scripts/check_chunking.py` + `scripts/fixtures/`，离线回归。

两个实现期发现，都影响了最终方案：

1. **行首已粘连的序号（`1.50N` 本就在一行）不能自动还原。** 原打算用「相邻序号从 1
   递增」判定是列表，实测会误伤真实数据——信用卡文里这样的返现比例列表很常见：

   ```
   1.5% 境内消费
   2.0% 境外消费
   ```

   按递增规则会被改写成「第1项：5%」「第2项：0%」，把正确数字毁掉。改为
   `find_glued_numbering()` 只捞出可疑行给人看，不自动改。**若真实万豪原文属于这种
   形态，本次修复对 bug 2 无效**，需要按那篇的具体排版另想办法。

2. **同块断言必须扫多个 `max_len`。** 最初只在线上值单点测试，夹具「通过」了，
   但换算法对照才发现旧实现在同一夹具上也通过——列表短的时候碰巧装得下，测试是空的。
   改成扫 `(600, 1000, 1500, 2500)`，并把列表条目加长到接近真实攻略的啰嗦程度后，
   旧实现在 4 个值里挂 3 个（含线上实际用的 1000），新实现全过。

### 2026-09-19 · 真实夹具已抓，bug 1 确诊、bug 2 判定

`backend/.venv` 里只装 requests/bs4/openai/python-dotenv（不装 chromadb，`store`
是 `_run_parse` 里的局部导入），抓下真实正文 8184 字存为 `scripts/fixtures/marriott.txt`。

**bug 1：确诊，刀口逐字吻合。** 拿 git HEAD 的原版 `_split_text` 跑真实夹具：

```
原版 9 块   50N→第7块   75N→第8块   ✗ 被切散
第 7 块末尾：…四、会员的里程碑奖励 / 1.50N 礼遇 / 5 晚套房券（NUA）/：目前已涵盖 / 丽思卡尔顿 / 和 / 艾迪逊
```

结尾与 spec 记录的入库残留「1.50N礼遇：5晚套房券（NUA）：目前已涵盖丽思卡尔顿和艾迪逊」
一字不差——刀就落在「艾迪逊」后面。新实现在 `max_len` 600/1000/1500/2500 下均同块，
已写进 `marriott.expect.json` 做回归。

**bug 2：真实原文是粘连形态，`normalize_numbering` 对这篇无效。** 原文里
`1.50N 礼遇` 本就在一行（上一条 Comment 担心的正是这种情况）。但它很可能是
**bug 1 的下游症状**：`PARSE_SYSTEM:76-77` 那条指令逐字点名了「『1.50N礼遇』其实是
『第2项：50N礼遇』、『2.75N』是『第2项：75N』」，具体到这个程度还失效，最可能的解释
就是那个块里根本没有 `2.75N`——它在第 8 块。模型看到孤零零一个 `1.50N 礼遇`，
没有兄弟项作证，指令里的例子对不上眼前的文本。两档同块后指令才有依据可用。
**这是假设，要真实 `parse()` 才能证实**；若仍粘连，再针对这篇单独处理。

**`find_glued_numbering` 原实现信噪比是反的，已重写。** 它要求候选行**连续**，
而 `1.50N 礼遇` 与 `2.75N 礼遇` 之间隔着 8 行解释文字，真正的目标整组漏报；
报出来的却是 `2.终身金卡：…` 这类点后接中文、没人会读成小数的行（全文 17 行）。改为：

- `_GLUED_NUM` 收紧到**点后必须是数字**——只有这种才有小数歧义。17 行噪声清零。
- 判据改为「前导序号构成从 1 开始的递增链」，不要求相邻，链内两项最多隔 60 行。
  多级编号 `4.1`/`4.2`/`4.3` 前导相同，自然落不进链里，也被排除。

真实夹具上现在恰好只报 2 行，就是 313/322 那两档。误伤红线 `1.5% 境内消费` /
`2.0% 境外消费` 仍会被**报告**（只报不改，人眼一眼能判），改写行为依旧为零。

另：真实里程碑**只有 50N / 75N 两档**，合成夹具里的 100N/125N 是虚构的。
合成夹具保留——它测的是孤立序号行形态，真实夹具测的是粘连形态，两者互补。

### 2026-09-19 · 终验通过，bug 2 确认为 bug 1 的下游症状

拿真实夹具跑了 `parse()`（GLM-4.5-Air，不入库）。含里程碑的第 5/6 块输出：

```json
{"domain": "hotel", "subject": "万豪", "subtopic": "里程碑奖励",
 "source": "公众号-小野狼的常旅客-万豪攻略",
 "text": "50N 礼遇：5 晚套房券（NUA）：…完整… 75N 礼遇：1 晚免费住宿（FN）：…完整…"}
```

两档合成一条完整片段，**序号被正确剥离**：`1.50N 礼遇` → `50N 礼遇`、
`2.75N 礼遇` → `75N 礼遇`，没有粘成小数。整篇 6 块跑下来共 35 条片段，
全局扫 `\d\.\d{1,2}N` 形态的粘连残留为 **0**。

这证实了上一条的假设：**bug 2 是 bug 1 的下游症状**。`PARSE_SYSTEM:76-77` 那条指令
本身没问题，它此前失效只是因为块里没有兄弟项可作证据。两档同块后指令自己就生效了，
**不需要在数据层还原行首粘连序号**——这也正好躲开了 `1.5% / 2.0%` 那条误伤红线。
`find_glued_numbering` 保持只报告不改写是对的定位。

一处要留意的抖动：整篇跑那次，模型把两档拆成了**两条**片段，且档位名没落在 `text`
开头而是进了其它字段；单块重跑则合成一条、档位名在 `text` 里。输入块逐字相同，
差异来自 LLM 自身（`temperature=0.1` 仍有抖动）。两次都满足验收口径
「两档都完整提取、序号不粘成小数」，但**片段粒度不保证稳定**，
今后若发现检索召不到某一档，先怀疑这里而不是切分。
